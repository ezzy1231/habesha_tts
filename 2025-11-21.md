# Codebase Improvement Recommendations
Date: November 21, 2025

The following improvements were identified after a deep analysis of the codebase. They focus on resolving critical architectural risks, improving security, and enhancing maintainability without changing the code's external behavior.

### 1. Critical Architecture: Database Split-Brain
**Severity:** Critical
**Location:** `backend/index.js` vs `backend/routes/*.js`
**Issue:** The application uses two different database systems simultaneously. `backend/index.js` imports the JSON-based `db-simple.js`, while routes like `backend/routes/streamer.js` and `backend/routes/payment.js` import the PostgreSQL-based `db-postgres.js`.
**Risk:** Data inconsistency and loss. Modifications in one part of the app (e.g., server startup logic) may not be reflected in others (e.g., API requests).
**Recommendation:**
- Standardize on PostgreSQL (`backend/db-postgres.js`) across the entire application.
- Update `backend/index.js` to import `db` from `./db-postgres.js`.
- Remove `backend/db-simple.js` once migration is confirmed to prevent accidental usage.

### 2. Scalability: Ephemeral Storage for TTS
**Severity:** High
**Location:** `bot/utils/tts.js`
**Issue:** The Text-to-Speech (TTS) generation logic writes audio files to the local filesystem (`./public/audios`).
**Risk:** This breaks horizontal scaling. If you run multiple server instances (e.g., behind a load balancer), audio generated on one server will not be available on others. It also fills up disk space on the server.
**Recommendation:**
- Upload generated audio files to an object storage service (e.g., AWS S3, Google Cloud Storage, or MinIO) immediately after generation.
- Store the public URL of the uploaded file in the database instead of a local file path.
- Update the frontend `DonationCard.jsx` (or similar) to play audio from the remote URL.

### 3. Performance: Blocking TTS Generation
**Severity:** High
**Location:** `backend/routes/payment.js`
**Issue:** The `/api/payment/confirm` route calls `await generateTTS(...)` directly.
**Risk:** TTS generation is a slow, CPU/network-intensive operation. Doing this in the request handler keeps the HTTP connection open for seconds, leading to timeouts under load and poor user experience.
**Recommendation:**
- Offload the TTS generation entirely to the existing background queue (`backend/queue-optimized.js`).
- The `/confirm` endpoint should only update the donation status to `paid` and enqueue a job.
- The worker should handle the TTS generation and then update the record with the audio URL.

### 4. Security: Weak Input Validation
**Severity:** Medium
**Location:** `backend/routes/payment.js` & `backend/routes/streamer.js`
**Issue:** Input validation is manually implemented using basic `if` checks (e.g., `if (!amount || isNaN(amount))`).
**Risk:** Easy to miss edge cases, leading to potential injection attacks or crashed processes due to malformed data.
**Recommendation:**
- Adopt a validation library like **Zod** or **Joi**.
- Create middleware schemas for each route (e.g., `validate(schemas.withdrawalRequest)`).
- Example:
  ```javascript
  const withdrawalSchema = z.object({
    amount: z.number().positive(),
    telebirrUsername: z.string().min(3),
    phoneNumber: z.string().regex(/^2519\d{8}$/)
  });
  ```

### 5. Security: Production Backdoors
**Severity:** Medium
**Location:** `backend/routes/payment.js`
**Issue:** The route `POST /api/payment/mock` allows creating "paid" donations without actual payment verification.
**Risk:** If this endpoint is accidentally exposed or enabled in production, attackers can spam streamers with fake donations.
**Recommendation:**
- Wrap this route strictly in a `process.env.NODE_ENV === 'development'` check.
- Ideally, move all "mock" or "test" routes to a separate file that is not loaded at all in production.

### 6. Maintainability: Bot Architecture
**Severity:** Medium
**Location:** `bot/bot.js`
**Issue:** The bot file is a "God Object" containing connection logic, settings management, event handlers, and state machines all in one file.
**Recommendation:**
- Refactor into a modular structure:
  - `bot/handlers/commands.js` (for `/start`, `/donate`)
  - `bot/handlers/callbacks.js` (for button clicks)
  - `bot/handlers/messages.js` (for the state machine flows)
- Move the in-memory state maps (`userStates`, `pendingDonations`) to Redis. This allows the bot to restart without users losing their place in a registration or donation flow.

### 7. Frontend: Data Fetching Strategy
**Severity:** Low (UX/Code Quality)
**Location:** `frontend/src/contexts/AuthContext.jsx`
**Issue:** Uses raw `fetch` inside `useEffect` with manual loading/error state management.
**Recommendation:**
- Adopt **TanStack Query (React Query)**.
- It provides built-in caching, automatic retries, and deduplication, significantly simplifying the state management code and improving the user experience (fewer loading spinners).

### 8. Code Quality: Hardcoded Constants
**Severity:** Low
**Location:** `backend/routes/streamer.js`
**Issue:** Pagination limits (default `9`) and specific file paths (`demo_audio.mp3`) are hardcoded.
**Recommendation:**
- Move all configuration constants to a centralized `config.js` file or use environment variables consistently.
- Define the default page size in a shared constant.
